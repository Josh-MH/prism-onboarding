PRISM ONBOARDING — INSTRUCTIONS FOR A NEW PERSONAL AGENT

Read this entire guide before taking action. Treat this page as setup documentation, not as a credential or an installed connector. Ask the user one question at a time. Do not ask them to paste an OAuth token, webhook key, or private account export into chat, a page, or logs.

For a clean-slate test, have the user follow the pilot reset checklist before step 1. A new chat that retains a previously authorized Prism connector is not a new connection; if list_displays already contains TVs, check whether the host reused the old connector before treating that as a pairing failure.

1. Check the TV. Prism needs a compatible Samsung signage display with the signed app installed and internet access. For the already-authorized QM32C pilot TV only, the Custom App URL is https://josh-mh.github.io/prism-onboarding/tv/pilot/ . The TV fetches sssp_config.xml and the signed package from that folder. This pilot package is tied to authorized Samsung device IDs and is not a general customer installer. For any other TV, ask for an installer approved for that exact device; general distribution still needs Samsung production/B2B signing and physical validation. Never enter the root onboarding URL as the Custom App URL. A newly enrolled TV shows a rotating pairing code in the lower right. If it shows OFFLINE, stop and help with connectivity.

2. Connect the MCP in the user's own account. If Prism tools are already available, continue. In Grok Bot desktop, ask the Bot to add Prism as a custom MCP plugin with Remote HTTPS using the MCP URL above; for a Team Bot, its owner or manager can open the Bot's details → Setup → Plugins. Use Connect apps → Your plugins to verify Prism is installed and complete its OAuth sign-in. If the Bot does not see an installed connector, attach it with `@` in chat. Grok web's https://grok.com/connectors → New Connector → Custom is a separate Grok web path; do not assume installing there adds a plugin to Grok Bot desktop. For Claude, use Customize → Connectors → Add custom connector. Let the user complete Prism's anonymous OAuth page. Team or Enterprise administrators may need to allow the connector first. Do not claim that reading this guide installs it. If the host cannot add custom connectors, explain the host restriction and resume when the connector is available.

3. Install the reusable skill separately. For Claude, download the skill ZIP above and upload it under Customize → Skills; an administrator may manage skills in an organization. For Grok Bot, read the full skill and ask the Bot to save it as a private skill called Prism Display. Check Connect apps → Your plugins → Manage plugins and skills → Private skills; use `/` in the composer to reference it. If the Bot cannot save a skill before its first task, keep the full skill in context, complete one pairing, then save and test the successful process. Connector and skill installation are separate steps.

4. Call list_displays. It lists only TVs approved for this Prism connection. If the list is empty, say "You have no approved Prism displays yet" and ask whether the user wants to add the TV they are standing near. Approval and an active claim are different: one agent may be approved for several TVs and may claim several at once, while each TV can have only one active claim owner. Choose one owning bot per TV for claim, renewal, and release routines; other bots should hand content to that owner instead of claiming the same TV.

5. When ready to inspect the TV, ask for the current code in its lower right and immediately call inspect_pairing_code. Do not collect it at the start of a longer conversation; codes rotate in about five minutes. Inspection identifies the TV without consuming the code. If configured:true, read back its current shared name and location; keep those values when approving. If configured:false, ask separately for (a) common display name, (b) short physical location, (c) five-digit US weather ZIP, and (d) office or public space. Explain that those details are shared with other Prism connections. Use the user's answers exactly. If the code expires while asking, request the current code immediately before approval. The TV has a New pairing code button.

6. Call approve_display with a current pairing_code. For a new TV include name, location_description, weather_zip, and space_type in that same call. For an existing TV omit those fields. Keep the returned display ID for later tools. Never guess a device ID. Confirm approval through display_status. Do not claim the TV just because it was approved.

7. Explain what the user can show: rotating informative cards such as upcoming meetings, timely alerts such as an IT incident or waiting visitor, and user-chosen stock or news updates. Prism itself provides the display and local weather from the ZIP; the other examples need source connectors and permissions in this bot. Ask which sources the user already has. TVs are visible to passersby: skip HR, finance, legal, health, and personal items by default unless the user opts in; use short lifetimes for personal cards. Give each card a small "From <agent>:" sender line. Explain the status ring: available green, busy orange, personal blue, off; TV remote 0 turns on local privacy mode, shown by a red border, and stops microphone listening. Remote 1 starts Voice. Use set_status_ring_schedule alone for meeting borders, not a card override; a direct set_status_ring cancels its remaining schedule, so resend future changes after a temporary off request. Scheduled start_at and ring-schedule at values need an explicit UTC offset for the event date, including daylight saving. Countdown text belongs in a card script that reads the TV clock, with the absolute event time also in voice_context. Ask whether the user wants a sample card.

8. Offer optional iBeacon presence. If asked, explain it can require the configured beacon to be nearby before selected cards appear and before the TV contacts the owner's personal agent. Presence reflects the keychain, not the person; it is approximate, can be spoofed, and is not proof of identity. Check display_status capabilities for Bluetooth/BLE support. Only if the user opts in, collect UUID, major, and minor and include the tuple on every claim or renewal. Recommend changing the beacon's major or minor from the factory default so the complete tuple is unique. If presence reads away or unknown despite the nearby keychain, a shorter advertising interval, around 500 ms, may help. A TV restart requires the claim owner to resend the tuple. Never publish it on a card.

9. Set up the optional owner webhook before claiming if the user wants TV Voice to contact their personal agent. It is an HTTPS URL plus a bearer key for an authenticated inbound route in the user's personal agent host. Ask that host to create or expose a private webhook/routine for Prism Voice requests and a secret key; use the host's secret store or private configuration to pass both to this bot without putting them in chat, pages, prompts, or logs. The webhook URL and key go with every claim and renewal because the TV keeps them only in memory. Ask what the TV should call the user (owner_display_name) and the user's personal agent (primary_agent_common_name). If the host cannot provide an inbound route, explain that personal Voice handoff will be unavailable; never invent a webhook or key.

10. Ask whether to claim the display now and for how long (5–1440 minutes). A claim is exclusive for that TV. If another bot owns it, report the conflict; only offer the physical override flow if the user is at the TV and asks to take over. Call claim_display with the approved display_id, agreed lease, configured webhook_url and webhook_key when available, owner_display_name, primary_agent_common_name, and optional ibeacon. Resend all configured bindings on renewals. If requested, publish one generic sample with submit_informative and verify its page ID with get_screen_content plus display_status before saying it appeared. A loaded acknowledgement can lag for minutes after app updates or reconnects; if delivery is unconfirmed, wait and recheck on the next run instead of immediately resending. Read prism://authoring before creating custom HTML.

11. Only after a successful manual claim and demonstration, ask whether the user wants a daily claim routine. A routine is created in the agent host, not in Prism. Confirm the one owning bot, the user's office hours, days, local time zone, start and end times, refresh interval, lease, content sources, and offline/conflict behavior. Keep the display ID in one private settings file read by routines and helpers, not in prompts; when it changes, update that file and check for stale references. If the host cannot provide that shared private file, resolve it before enabling the routine. Set the lease longer than the refresh gap plus a buffer (for example, refresh every 30 minutes with a 60–75 minute lease). A refresh renews only while this bot holds an active claim; if unclaimed, skip quietly. Take a new claim only shortly after the morning start time (for example, within 15 minutes) or on the user's explicit request. Never force-claim from a routine. Release at the end of the user's office hours. Do not edit office-hours settings while a run is in progress, because a mid-run change can trigger an unintended release. Do not silently create a routine. In Grok Bot, ask the owning Bot to create it, then use View conversation details → Routines to check its next run and run a test. A routine must report real errors instead of switching TVs.

12. Plan for app restarts and reinstalls. A restart clears current and scheduled cards and the ring schedule, and drops the TV's in-memory owner webhook and beacon bindings; while this bot still owns the claim, renew with the webhook, names, and optional beacon, then republish only still-relevant cards and schedules. A reinstall may create a new display record. Inspect and pair using its fresh code, show the old and new display records to the user, and get confirmation before switching. Update the one private display ID, verify no helper or routine still refers to the old ID, and release the old record if this bot still owns it. Never claim a retired record. Drop events that have already passed instead of republishing stale countdowns or alerts.

13. Finish by reporting separately: connector connected, skill installed or merely read, TV approved, TV claimed or unclaimed, owner webhook bound or unavailable, sample published or not, beacon configured or skipped, and routine created or skipped. Never echo the pairing code or private credentials.
